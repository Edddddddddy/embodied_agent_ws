# 项目知识点笔记

这份笔记按一条语音指令从麦克风进入、最终变成电机控制帧的顺序，解释项目涉及的主要知识点。具体文件位置见 [`PROJECT_NOTES.md`](PROJECT_NOTES.md)，测试方法见 [`TESTING_GUIDE.md`](TESTING_GUIDE.md)。

## 1. ROS 2：把不同实时特性的模块连接起来

ROS 2 的基本单元是节点，节点通过 topic 异步发布和订阅消息。本项目把音频、模型和硬件拆开，是因为三者的实时性、依赖和故障模式不同：

- C++ 节点负责 PortAudio、AEC/VAD、动作校验、UART/SPI 等靠近系统和硬件的部分。
- Python 节点负责云 SDK、sherpa-onnx、llama.cpp HTTP 流、提示词、记忆和对话编排。
- 两侧只交换 ROS 消息，模型实现可以替换而不必修改底层驱动。

这里还涉及几个 ROS 2 概念：

- **参数**：采样率、静音阈值、模型路径和串口配置写在 YAML，通过 launch 注入。
- **launch**：一次启动多个节点，并为在线、离线、mock、硬件模式提供不同组合。
- **QoS**：音频采用 `BEST_EFFORT + KEEP_LAST`，允许在系统过载时优先保留实时性；动作和状态更重视可靠送达。
- **话题解耦**：`/agent/action_candidate` 是模型候选，`/robot/action_command` 是校验后的可信命令，两者不能混用。

## 2. 数字音频与实时线程

项目使用单声道 PCM16。PCM16 表示每个采样点是 16 位有符号整数；16 kHz 意味着每秒 16000 个采样点。20 ms 的一帧包含 320 个采样点、640 bytes。

PortAudio 回调属于实时路径，不能在里面做网络请求、模型推理或阻塞磁盘操作。正确做法是回调只复制数据到有界队列，由普通工作线程完成 AEC、VAD 和 ROS 发布。队列有上限是为了让过载显性化，避免无限积压把“实时系统”变成“越来越旧的录音回放”。

在线 TTS 输出 24 kHz，离线 Melo-TTS 模型输出 44.1 kHz，而 ASR 输入是 16 kHz，因此测试回灌时需要重采样。采样率配置错误会导致语速、音高和识别结果同时异常。

## 3. AEC、VAD 与 0.4 秒静音断句

### 回声消除

扬声器播放 TTS 时，麦克风会重新采到机器人的声音。AEC 使用已知的播放参考信号估计回声，再从麦克风信号中减去。当前实现是 NLMS 自适应滤波基线：

```text
误差 = 麦克风输入 - 滤波器(扬声器参考)
权重更新量 ∝ 误差 × 参考 / (参考能量 + ε)
```

NLMS 能自动适应一定范围内的声学路径，但真实机器人仍需标定滤波长度、步长和播放延迟。单元测试只能证明算法收敛，不能证明真实房间里的双讲、混响和 ERLE 达标。

### VAD 与静音超时

能量 VAD 计算一帧的 RMS/能量并与阈值比较。检测到语音后，如果连续 0.4 秒都低于阈值，就发布一次 `/audio/silence_timeout`。在线 ASR 和离线 ASR 都以这个事件作为 commit 边界，因此“0.4 秒”只在音频前端维护一份。

阈值过低会把环境噪声当语音，过高会吃掉轻声说话。实际部署应采集安静、风扇、电机和播放 TTS 四种场景的能量分布后再定阈值。

## 4. 流式 ASR 与唤醒词

流式 ASR 不等待整段录音结束，而是持续接收小块 PCM，维护解码器状态，并产生 partial/final 文本。项目有两种 provider：

- 在线模式使用 Qwen Realtime ASR，通过 WebSocket 推送音频。
- 离线模式使用 sherpa-onnx 的 ZipFormer Transducer。Encoder 提取声学特征，Decoder 建模已输出 token，Joiner 给出下一 token 分布。

`commit-to-final` 只表示提交后得到 final 的时间；完整用户感知延迟还包括 0.4 秒静音等待和前面的实时音频处理，测量时必须区分。

当前唤醒词是文本门控：ASR final 中出现“小智”后，在激活窗口内接受指令。它简单且可测试，但短唤醒词容易被 ASR 识别成同音字。真正的产品通常会增加专用 KWS、hotword bias、误唤醒率和漏唤醒率评测。

## 5. LLM 流式推理、提示词与结构化输出

LLM 使用 token 流而不是等待完整回答。首 token 到达后，增量解析器分别提取：

```text
<speech>可朗读文本</speech>
<action>{"name":"move","arguments":{...}}</action>
```

`SentenceChunker` 遇到标点或长度上限就把已有文字送给 TTS，因此 LLM 仍在生成后文时，前一句已经可以合成。首 token 延迟不等于首音频延迟；后者还受首个可断句标点和 TTS 建连影响。

系统提示词承担角色、输出协议和动作范围约束；对话记忆使用有界历史并原子落盘，避免历史无限增长和半写文件。模型输出仍是不可信输入：JSON 能解析不代表动作语义正确，所以动作不能从 parser 直接进入电机。

在线节点在 ready 前执行最小 LLM 预热并建立持久 TTS WebSocket。这样稳态请求可以复用连接，但报告性能时仍必须分别记录冷启动和预热数据。

## 6. 在线全流式 TTS 与离线伪流式 TTS

在线 Qwen TTS 使用持久 WebSocket。每轮把文本片段 `append` 到当前响应，使用 `commit` 结束本轮；只有节点退出时才 `finish/close` 整个会话。若每轮都重新连接，TLS/WebSocket 建连成本会直接进入首音频延迟。

离线 Sherpa-TTS/VITS 通常以完整句子合成，项目通过两层方式实现伪流式体验：

1. LLM 文字按句尽早进入 TTS worker。
2. 合成后的 PCM 再切成约 80 ms 小块发布和播放。

这不是声学模型内部的真正增量生成，但能让 LLM 和 TTS 异步重叠，减少句间卡顿。

## 7. 并发、双缓冲与背压

离线链路使用容量为 2 的消息缓冲和音频缓冲：

```text
LLM worker -> [句子 A | 句子 B] -> TTS worker
TTS worker -> [PCM A  | PCM B ] -> ROS/播放
```

容量 2 可以让生产者和消费者短暂错峰，又不会积压太多旧数据。消息缓冲使用无损等待，不能静默丢掉一句话；实时音频在必要时允许丢最旧块以追上当前播放位置。`close` 表示正常排空，`abort` 表示异常时立即唤醒并终止消费者，二者语义不同。

## 8. llama.cpp、Q8 量化与 LoRA

llama.cpp 用 GGUF 模型在 CPU 上推理，并通过本地 OpenAI 兼容服务向 ROS 节点提供流式 token。项目使用 Qwen3-0.6B Q8_0：8 bit 量化降低权重内存和带宽，但 Q8 相对 FP16 通常接近缩小一半，不能天然表述为“压缩至 25%”。压缩比例必须用同一模型的实际文件大小计算。

LoRA 不直接改动全部基础权重，而是为选定线性层训练低秩增量，适合小数据、低显存的指令微调。`training/` 已准备 LLaMA-Factory 配置和种子数据，但训练暂未执行。模型动作准确率必须在冻结且独立的测试集上测，不能用训练样本或确定性规则的成绩代替。

## 9. 动作解析、安全仲裁与硬件协议

动作经过多层防线：

1. Python parser 只接受合法 `<action>` JSON。
2. 明确短命令由确定性语义解析仲裁；否定、疑问和危险组合阻断模型动作。
3. C++ `ActionValidator` 检查动作白名单、参数 schema、类型并限幅。
4. `HardwareController` 编码版本号、序号、长度、payload 和 CRC。
5. UART/SPI transport 发送帧；watchdog 到时自动发送 stop，急停拥有独立入口。

确定性仲裁提高了工程可用性，但不能掩盖基础模型的准确率。最终机器人还应有独立于 Agent 的碰撞检测、限流、姿态保护和硬件急停。

UART 是异步字节流，易调试且常见于 MCU；SPI 是主从同步总线，吞吐高但需要片选、模式和时钟一致。项目用 Linux PTY 测真实 UART 系统调用，用 mock transport 测完整 ROS 回执；实体设备仍需示波器/逻辑分析仪和电机断电条件下先验帧。

## 10. 延迟与正确性应该怎样测

关键指标不是一个总时间：

- ASR finalization：commit 到 final。
- LLM first token：请求发出到第一个 token。
- TTS first audio：首段文字提交到第一个 PCM 包。
- End-to-first-audio：静音边界到用户听见回复前的近似值。
- Turn complete：静音边界到本轮 LLM/TTS/动作全部结束。
- RTF：计算耗时 / 音频时长；小于 1 才能实时运行。

正确的性能结论要固定机器、线程数、模型、网络地域、冷热状态和文本长度，运行足够样本后报告 P50/P95。功能单元测试、链路冒烟测试、模型准确率和性能基准是四类不同证据，不能互相替代。

## 11. 设计原则总结

- 实时回调只做有界、可预测的工作。
- 依赖通过 provider interface 隔离，mock 与真实实现使用同一编排。
- 不可信的模型输出必须经过语义和 schema 双重校验。
- 在线连接尽量复用，离线任务用有界队列并行。
- 每个指标在产生它的模块旁测量，同时保留端到端测量。
- 文档明确区分“代码已实现”“当前样本通过”和“可正式宣称达标”。

## 12. Gazebo、DDS、TF2 与差速机器人

Gazebo 负责世界、刚体动力学、轮地接触和激光雷达；ROS 2 节点不直接调用仿真内部 API，而是通过 `ros_gz_bridge` 交换标准消息。`geometry_msgs/Twist` 的 `linear.x` 和 `angular.z` 进入差速驱动插件，Gazebo 输出 `/odom`、`/tf` 和 `/scan`。这样同一个上层控制器未来可以切换到实体 TurtleBot3，只需更换执行后端。

DDS 是 ROS 2 的通信底座，负责节点发现、序列化和 QoS。仿真测试为每次运行设置独立 `ROS_DOMAIN_ID`，避免旧 Gazebo 或其他终端的 `/clock`、`/odom` 被当前测试发现。进程退出也必须按进程组清理，否则多套仿真会让里程计测量看似成功却完全不可信。

TF2 描述随时间变化的坐标系关系，例如 `odom -> base_footprint -> base_scan`。当前局部避障只使用机器人坐标系下的 LaserScan，不需要做全局坐标变换；下一阶段接 Nav2 和“前往某处”动作时，必须用 TF2 把地图目标、机器人位姿和传感器数据统一到正确坐标系。

沿墙控制把右侧距离误差输入 PID。P 决定当前修正强度，I 消除长期偏差但容易积分饱和，D 抑制快速变化但对雷达噪声敏感。本项目默认 `ki=0` 并限制积分，先获得稳定基线，再在固定世界和固定速度下调参。
