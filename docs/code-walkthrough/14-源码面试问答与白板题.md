# 14 源码面试问答与白板题

## 1. 回答源码题的固定结构

不要从组件名开始堆技术栈。推荐顺序：

```text
结论 -> 一条真实调用链 -> 关键状态/数据 -> 为什么这样设计
     -> 测试证据 -> 当前边界
```

常规回答控制在 5 到 8 句。面试官继续追问时再展开代码。

## 2. 节点交互

### Q1：一条语音命令如何变成 `/cmd_vel`？

麦克风 PCM 先进入 C++ AudioFrontend，经过 NLMS AEC、能量 VAD 和静音断句后发布 clean PCM。在线或离线 Agent 将 PCM 送入 ASR，final transcript 经过唤醒门控，再进入流式 LLM；增量 parser 把 speech 和完整 action 分离。action candidate 只是非可信 JSON，C++ Guard 做精确 schema、白名单和限幅，转成 `RobotCommand`。typed bridge 把命令发送为 `ExecuteRobotCommand` goal，SimulationControl 用 BT 和 ActionExecution 管理执行。20 Hz control tick 从 executor 取安全速度并发布 `/cmd_vel`，Gazebo bridge 再驱动 TurtleBot3。最终要结合 Action result、BT status 和 odom 位移证明闭环。

### Q2：项目用了哪些交互模式，为什么？

音频、雷达、状态和急停是事件流，用 Topic；音频和 scan 采用 best effort，命令/result 使用 reliable。运动是持续任务，需要 goal、feedback、cancel 和 result，所以默认用 Action。Lifecycle transition 是短请求，底层使用 Service。Parameter 用于启动配置，Timer 驱动 20 Hz 控制循环。选择依据是交互语义，不是某个接口“更高级”。

### Q3：QoS 不匹配会怎样定位？

先确认 Topic 名和 namespace，再用 `ros2 topic info -v` 比较 publisher offered 与 subscriber requested QoS。音频和 scan 使用 best effort SensorDataQoS，若消费者强制请求不兼容策略，可能 Topic 可见却收不到样本。再用 `ros2 topic hz` 判断是完全无数据还是频率不足。若 DDS 图发现正常，还要查 ROS_DOMAIN_ID 和 middleware。项目把控制命令设为 reliable，避免沿用音频 QoS 导致关键命令可丢。

## 3. 音频与模型链

### Q4：NLMS AEC 的核心公式和线程路径是什么？

扬声器 PCM 是参考 `x`，麦克风是 desired `d`，滤波器预测回声 `y=w^T x`，输出误差 `e=d-y`。权重按 `w += μ e x /(ε+||x||²)` 更新，所以比 LMS 对音量变化更稳定。PortAudio callback 只把 20 ms PCM 放入有界队列，processing thread 做 AEC/VAD；playback thread 在写声卡前把 TTS PCM 加入 reference。reference 从 24 kHz 线性重采样到 16 kHz，并插入固定延迟。边界是没有 double-talk detection、频谱降噪和专业 resampler，真实设备需要标定。

### Q5：VAD、静音断句、热词、唤醒有什么区别？

VAD 只根据一帧 RMS 判断有无语音。静音检测要求先听到 speech，再累计 400 ms non-speech 才 commit。ASR hotword 是解码偏置，让“小智”等文本更可能被识别。WakeWordGate 工作在 final transcript 上，决定是否授权对话，并支持 10 秒 follow-up window。它们分属音频端点、解码和业务授权，不能混称为“唤醒算法”；当前也没有独立声学 KWS。

### Q6：在线和离线 ASR 为什么都用 commit？

音频前端统一决定句尾，上层 provider 只接收连续 PCM 和 commit。在线 adapter 在 WebSocket 中 append base64 PCM，commit 后等待 completed transcript；离线 ZipFormer 在单 worker 中 accept waveform，commit 时 input_finished、解码尾部并重建 stream。这保证在线/离线共享同一 VAD 和 Agent 编排。代价是本地 VAD 误判会同时影响两条链路。离线还要有队列，避免 native recognizer 被多个 ROS callback 并发访问。

### Q7：流式 TTS 怎样降低延迟，又怎样防止半个 action 执行？

TaggedStreamParser 对 speech 和 action 采用不同策略。speech 在确认不会属于闭标签后就增量释放，再按标点或长度切句给 TTS；action 一直缓存到完整 `</action>`，随后才 JSON parse。在线 TTS 复用持久 WebSocket，LLM、TTS、播放重叠。离线 VITS 按句生成，再切成 80 ms PCM，通过容量为 2 的 buffer 做背压。这样首音频更快，同时不让半个 JSON 成为命令。

## 4. 动作安全

### Q8：为什么需要 Python fallback 和 C++ Guard 两层？

fallback 解决有限自然语言的确定性语义，例如否定、疑问和常见同义命令，减少小模型误动作。Guard 不理解自然语言，只验证可执行结构：JSON、exact keys、类型、动作白名单和范围。Python 层可能有 bug、被替换或被其他 ROS publisher 绕过，所以物理副作用前必须由 C++ 本地验证。之后 Action server 和 controller 还分别检查 typed goal 与实时雷达。它们是互补的纵深防御，不是重复代码。

### Q9：为什么 exact key schema 很重要？

只检查必需字段会接受额外字段，而不同下游可能对额外字段有不同解释。Guard 要把模型输出压缩为唯一规范命令，所以 expected key set 必须等于 actual set。这样 legacy JSON 和 typed adapter 不会产生语义分歧。缺字段、多字段、错误类型都给出确定性 rejection。代价是协议扩展必须同步升级校验器和消费者，但机器人控制更需要明确失败而不是猜测。

### Q10：为什么 Guard 不能负责所有安全？

Guard 能判断速度和时长是否在静态范围内，却不知道前方实时是否有障碍、scan 是否过期或底盘是否执行。动态安全需要传感器状态，位于 controller/executor。若 Guard 订阅所有传感器，它会与具体机器人强耦合，在线、离线、Gazebo 和硬件难以复用。项目让 Guard 形成可信意图，让执行层根据实时环境决定 blocked。最终物理急停仍应独立于 LLM 和普通软件链路。

## 5. Action 与 BT

### Q11：Action 的成功、取消、超时、阻塞怎样区分？

`ActionExecution` 根据当前时间、cancel flag 和 safety blocked 产生领域状态，优先级是 cancel、blocked、hard timeout、duration success。BT 再把状态映射成 running/succeeded/canceled/timed-out/blocked outcome。Action result 有自定义 status 和 message，ROS result code 则是 succeed、abort 或 canceled。所有 duration 终态统一先调用 executor stop。测试分别覆盖五种路径，避免只用一个 bool 表示所有失败。

### Q12：新 goal 如何抢占旧 goal？

`handle_accepted()` 发现 `active_goal_` 时先 halt/cancel 旧 BT，再以 `preempted_by_new_goal` 结束旧 Action，然后启动新命令。由于旧 goal 不是客户端 canceling，ROS result code 走 abort，但自定义 status 是 CANCELED。stop 也是一个新 immediate goal，所以能抢占活动 move/turn。清理后再设置新 active state，防止两个 goal 同时拥有 executor。

### Q13：ReactiveSequence 为什么适合安全检查？

Execute 返回 RUNNING 时，ReactiveSequence 下一 tick 会从 Validate 和 Safety 重新开始。若 LaserScan 新障碍使 `safety_blocked=true`，CheckSafety 立即 FAILURE，并 halt running Execute。普通 Sequence 可能从 running child 继续，不会重新评估前置条件。真正 stop 仍由 Action server 的统一 finish 函数执行，BT 负责表达 outcome。这样安全条件是持续不变量而不是启动前检查一次。

### Q14：ConfirmResult 是否证明机器人到达目标？

没有。当前 ConfirmResult 只检查 `ActionExecutionState::kSucceeded`，即计时时长正常完成，没有 cancel/block/timeout。它不读取 odom、编码器或下位机 completed ACK。因此 BT confirm 是任务状态机证据，不是独立物理反馈。Gazebo 验收额外比较 odom 位移；真实硬件还需要下位机 sequence result 或外部定位。

## 6. 控制、并发和硬件

### Q15：沿墙 PID 怎么工作？

控制器取右侧 ±25° 扇区最小距离，误差定义为目标 0.4 m 减当前距离。右墙太近时误差为正，输出正 angular z，机器人左转远离墙。积分按 `error*dt` 累积并限幅，导数按误差变化率计算，最终角速度再 clamp。默认 Ki 为 0，所以实际是 PD；前方转角或模式切换会 reset PID。scan stale 时自主模式停车，防止使用旧测量。

### Q16：MultiThreadedExecutor 如何避免数据竞争？

多线程只让不同 callback group 有并行机会。控制相关 callback 留在默认 MutuallyExclusive group，diagnostics timer 单独放入另一个 MutuallyExclusive group。control tick 写 diagnostics snapshot、timer 读 snapshot，用 mutex 保护并在复制后释放锁；跨线程 active flag 用 atomic。diagnostics 不直接调用可变 executor。若未来把 control/action 放到 Reentrant group，现有串行假设需要重新审计。

### Q17：pluginlib 比 if/else 好在哪里？

核心节点只依赖 `RobotExecutor`，插件负责 configure、execute、stop、scan 和 step。Gazebo 和 mock 通过导出宏、XML、CMake 描述被 runtime class loader 发现，新增后端不修改 Action/BT。mock 让 CI 不依赖仿真，Gazebo 封装真实控制器。代价是安装、ABI 和描述文件错误更复杂；只有一个实现时 if 更简单。这个项目已有两个真实 adapter，所以替换点是有测试证据的。

### Q18：硬件 watchdog 与 ACK 的边界是什么？

move/turn 成功写出协议帧后，watchdog 按 duration 设 deadline，20 ms timer 到期主动发送 stop。stop 发送失败会 100 ms 后重试。ACK 的 `status=sent` 只说明主机验证、编码和 write/ioctl 成功，不说明下位机执行。协议已有 sequence 和 CRC，但当前没有解析下位机 completed frame。要形成任务闭环，需要下位机回传 accepted/completed/error 并映射到 Action result。

### Q18.1：当前 emergency stop 是完整急停吗？

不是。SimulationControl 的 emergency Topic 回调当前调用 executor stop 并发布 ACK，能让速度归零，但没有把 active Action 立即置为 canceled，也没有调用控制器已有的 `set_emergency_stop(true)` latch。所以下一条命令仍可运动，当前 goal 也可能继续到计时终态。面试中我会把它称为软件停车事件或急停入口，而不是完整硬件 E-stop。生产化需要原子地停车、终止任务、锁定运动、显式复位，并由独立硬件回路兜底。

## 7. Nav2

### Q19：定时 move 与 Nav2 导航差异是什么？

定时 move 只有速度和持续时间，没有目标位置闭环。Nav2 goal 是 map frame 的位姿，依赖 map/odom/base_link TF 和定位。NavFn 在 global costmap 上规划路径，DWB 根据 local costmap 采样局部速度，BT Navigator 处理重规划和恢复，collision monitor 做底盘前安全。语音主项目不能因此包装成已完成 Nav2；当前 Nav2 是独立 C++ 教程和配置。未来应由 Guard 校验目标，再让 executor 作为 NavigateToPose client。

### Q20：导航 client 订阅 scan，是否实现了避障？

没有。`Nav2Client::laserCallback()` 只保存最新 LaserScan，没有参与 goal 或速度计算。真正的 scan 消费者是 local/global costmap 和 collision monitor。client 主要负责目标 pose、Action feedback/result/cancel。判断“谁实现功能”要追数据在哪里被用于决策，而不是只看谁订阅了 Topic。

## 8. 白板题

### 8.1 画成功命令时序图

必须包含：AudioFrontend、Agent、Guard、Bridge、Action server、BT、Executor、Gazebo，并标出 candidate、typed command、goal、feedback/result、cmd_vel、odom。

### 8.2 画障碍中止状态图

必须说明：scan callback -> controller safety_stopped -> ActionExecution blocked -> ReactiveSequence Safety FAILURE -> stop -> Action abort/result BLOCKED -> final zero velocity。

### 8.3 画线程与队列图

至少区分 PortAudio callback、processing/playback thread、ROS executor、turn thread、TTS thread、offline ASR worker，并标出每个有界队列的满队列策略。

### 8.4 设计 `navigate_to_pose` 扩展

回答应覆盖 interface、Guard 坐标/frame 校验、Nav2 client、feedback/result 映射、cancel/stop、定位可用性、测试和事实边界。

## 10. 模拟面试验收

随机抽取三题：一题主链、一题并发/安全、一题边界。每题两分钟，必须：

- 点出至少两个真实类或函数；
- 描述一个失败分支；
- 给出对应测试或观测 Topic；
- 主动说明一个未完成能力。
