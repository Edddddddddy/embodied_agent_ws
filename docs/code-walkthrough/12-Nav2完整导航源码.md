## 1. 先区分两个控制层级

语音主项目的 move 是速度和时间命令：

```text
linear_x=0.2 m/s, duration=1.0 s
```

它不关心机器人最终在哪。Nav2 的 `NavigateToPose` goal 是地图坐标中的目标位姿：

```text
x=1.0 m, y=1.0 m, yaw=1.57 rad, frame=map
```

Nav2 必须持续回答：机器人当前在哪、目标在哪、可行路径是什么、局部障碍是否变化、该发什么速度、失败后怎么恢复。

## 2. 教程源码边界

导航示例位于另一个仓库目录：

```text
ros2-doc/ros2-src/nav2_cpp_tutorial/
```

其中 `Nav2Client` 是 Action client；全局规划、局部控制、costmap 和 BT 由 Nav2 开源组件提供，不是教程自己实现。

准确说法是“实现并理解 Nav2 C++ Action client，配置并集成 Nav2 组件”，不是“从零实现了 NavFn/DWB”。

## 3. 启动结构

`nav2_cpp_demo.launch.py`：

```text
TurtleBot3 Gazebo
  + nav2_bringup/bringup_launch.py(slam=true)
  + nav2_params.yaml
  + optional delayed nav2_simple_test
```

`slam=true` 时地图由 SLAM 流程在线构建，不使用固定地图 + AMCL 的经典定位模式。若部署已有地图，应切换为 map server + localization，并提供初始位姿。

## 4. 坐标系与 TF

导航至少涉及：

```text
map -> odom -> base_link -> sensor frames
```

- `map`：全局一致坐标，允许定位修正产生跳变；
- `odom`：局部连续坐标，短期平滑但会漂移；
- `base_link`：机器人机体坐标；
- laser frame：雷达安装坐标。

全局 costmap 使用 `map`，局部 costmap 使用 `odom`。目标默认在 map frame。TF 缺失或时间戳超出 tolerance 时，规划器即使有 scan 也无法正确放置障碍。

## 5. 创建目标位姿

`Nav2Client::createPoseStamped(x, y, yaw, frame_id)`：

```cpp
pose.header.frame_id = frame_id;
pose.header.stamp = now();
pose.pose.position.x = x;
pose.pose.position.y = y;
tf2::Quaternion q;
q.setRPY(0.0, 0.0, yaw);
pose.pose.orientation = tf2::toMsg(q);
```

ROS pose orientation 使用四元数，不直接传 yaw。平面机器人 roll/pitch 为 0，用 `setRPY` 转换。

frame_id 不是标签装饰。如果把 map 坐标误写成 base_link，目标含义会变成相对机器人当前位姿。

## 6. 发送 NavigateToPose Goal

`sendGoal()`：

1. 等待 `navigate_to_pose` server 最多 2 秒；
2. 构造 `NavigateToPose::Goal`；
3. 注册 feedback/result callback；
4. 清空本地 result 状态；
5. `async_send_goal()`；
6. 最多等 5 秒获得 goal handle；
7. handle 为空表示 server 拒绝；
8. 保存当前 goal handle。

虽然 API 名为 async，函数内部对 goal-handle future 做了同步 `wait_for()`。示例程序另启 spin thread，因此 callback 和 Action response 仍能被处理。若在单线程 executor 的某个 callback 内直接调用这个阻塞函数，可能造成 executor 无法处理 future 完成事件；生产代码宜保持全异步或使用独立 callback group/executor。

## 7. Feedback、Result 和 Cancel

feedback 读取：

```text
distance_remaining
number_of_recoveries
```

日志被 throttle 为每 2 秒，避免高频刷屏。完整 feedback 还可以包含当前 pose、navigation time 等，示例没有全部使用。

result callback 把 ROS Action result code 映射为：succeeded、aborted、canceled、unknown，并通过 condition variable 唤醒 `waitForResult()`。

`cancelGoal()` 使用当前 goal handle 发送 cancel，等待 cancel response 最多 3 秒。cancel 请求被接受后，最终仍要等待 result callback 才能确认导航进入 CANCELED。

## 8. 为什么测试程序需要 spin thread

`nav2_simple_test` 主线程顺序执行：send goal -> wait result -> 下一个 goal。另一个线程 `rclcpp::spin(nav2_client)` 负责：

- Action response；
- feedback；
- result；
- odom/scan subscription。

没有 spin thread，主线程阻塞等待 condition variable，而 callback 永远不会执行，形成死等。

共享 navigation status、pose 和 goal flags 用 mutex；result 使用 condition variable。`wait_for` 的 predicate 防止虚假唤醒。

## 9. Nav2 内部数据流

```text
NavigateToPose goal
  -> BT Navigator
     -> Planner Server / NavFn: map + global costmap -> global path
     -> Controller Server / DWB: path + local costmap + odom -> cmd_vel
     -> Behavior Server: spin/backup/wait 等恢复动作
  -> Velocity Smoother
  -> Collision Monitor
  -> base cmd_vel
```

BT Navigator 是任务编排层；planner 找路径；controller 跟路径；costmap 把地图和传感器转换为代价；collision monitor 是靠近底盘的额外安全层。

## 10. Global Costmap

配置：

- frame `map`；
- static layer：已有/SLAM 地图；
- obstacle layer：LaserScan marking/clearing；
- inflation layer：障碍周围扩张代价；
- resolution 0.05 m；
- robot radius 0.22 m。

inflation 不是简单把障碍变大，而是在周围产生递减代价，规划器倾向远离墙。radius/inflation 配太小可能擦碰，太大可能认为窄门不可通行。

## 11. Planner Server / NavFn

`GridBased` 使用 `nav2_navfn_planner::NavfnPlanner`：

```yaml
use_astar: false
allow_unknown: true
tolerance: 0.5
```

`use_astar=false` 通常走 Dijkstra 风格扩展；它在 global costmap 上生成从当前位姿到目标的路径。`allow_unknown=true` 允许规划穿过未知区域，适合 SLAM 探索场景但风险更高。

## 12. Local Costmap 与 DWB

Local costmap：

- frame `odom`；
- 3 m x 3 m rolling window；
- voxel layer 从 scan 标记/清除障碍；
- inflation layer。

DWB 采样候选 `(vx, vy, vtheta)`，向前模拟 1.7 秒轨迹，再由 critics 评分：障碍、路径对齐、目标对齐、路径距离、目标距离、旋转到目标等。差速机器人 `max_vel_y=0`。

它不是经典单个 PID；它在速度空间生成多条短期轨迹并选择代价最低且合法的一条。

## 13. BT Navigator 与 Recovery

Nav2 的 BT 比主项目四节点树复杂，通常包含：

- 计算/重算路径；
- 跟随路径；
- planner/controller error recovery；
- 清 costmap；
- spin、backup、wait；
- cancel/goal update。

`behavior_server` 配置 spin、backup、drive_on_heading 和 wait。恢复行为不等于保证成功，它们只是从局部失败中尝试脱困，最终仍可能 aborted。

## 14. Velocity Smoother 与 Collision Monitor

Velocity smoother 以 20 Hz 限制最大速度、加速度和减速度，减少控制器输出跳变。配置为 OPEN_LOOP，使用命令值而非实时速度反馈做平滑；若执行器跟踪差，闭环估计会更准确。

Collision monitor 订阅平滑后的速度和 scan，用 footprint approach 预测 1.2 秒碰撞并修改/阻断速度。它位于 planner/controller 之后，是更靠近底盘的安全层，但不能替代 costmap 规划。

## 15. 示例中的 odom 和 scan subscription

`Nav2Client` 自己订阅 odom 并保存 current pose，供 `getCurrentPose()` 使用；订阅 scan 后只保存 `current_laser_`，没有在 client 内做避障。真正消费 scan 做 costmap/collision 的是 Nav2 节点。

不要因为 client 有 `laserCallback()` 就说“C++ client 实现了激光避障”。

## 16. 如何接入语音主项目

未来可增加动作：

```text
navigate_to_pose {x, y, yaw, frame_id}
```

需要同步修改：

1. system prompt 和 `ActionCommand` schema；
2. C++ Guard 白名单、有限数、坐标范围和 frame 白名单；
3. `RobotCommand.msg` 或新增专用 Navigate command；
4. executor 增加 Nav2 Action client；
5. 把 Nav2 feedback/result 映射到上层 Action；
6. stop/cancel 同时取消 Nav2 goal；
7. 增加定位可用、map/TF 新鲜度和目标区域策略；
8. 用 odom/pose 与 Nav2 result 验收。

推荐让语音执行层作为 Nav2 Action client，不要从 LLM 直接发布 Nav2 goal，也不要绕过 collision monitor 直接控制速度。

## 17. 面试回答模板

**问题：导航是怎么实现的？**

主语音项目当前的 move 是定时速度控制，不是全局导航。仓库里的 Nav2 C++ 示例通过 `NavigateToPose` Action 发送 map frame 的 `(x,y,yaw)` 目标，yaw 先转成四元数。BT Navigator 负责导航任务编排，NavFn 在 global costmap 上生成全局路径，DWB 根据 local costmap 和 odom 采样短期速度轨迹并评分，velocity smoother 限制加减速，collision monitor 根据 scan 做底盘前的碰撞保护。Action feedback 提供剩余距离和恢复次数，result 区分成功、终止和取消。示例 client 自己订阅 scan 只用于保存观测，真正避障在 Nav2 costmap 和 collision monitor 中。未来接语音时仍要经过 Guard，再由 executor 作为 Nav2 Action client 发送目标。
