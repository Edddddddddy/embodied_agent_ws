## 1. 本章问题

ROS 2 提供 Topic、Service 和 Action，不是让开发者随意挑一个“能通信的”接口。选择依据是数据语义：它是连续事件、短请求，还是可取消的长任务？本项目三种语义都出现，但主链主要使用 Topic 和 Action。

## 2. Node 是什么

Node 是 ROS graph 中拥有名称、参数、publisher、subscription、service、action、timer 的逻辑参与者。Node 不等于进程：

- `audio_frontend` 默认一个节点一个进程。
- `simulation_control` 可以作为独立进程，也可以装入 component container。
- 一个进程可由 executor 调度一个或多个节点及其 callback。

Python 入口 `OnlineAgentNode(Node)` 和 C++ 入口 `SimulationControlNode(LifecycleNode)` 都在构造或 configure 阶段创建 ROS 接口，真正业务逻辑在回调中被 executor 触发。

## 3. Topic：连续事件流

Topic 是异步 publish/subscribe。publisher 不等待某个消费者返回结果，也不知道当前有几个消费者。

### 3.1 项目实例

在 `online_agent_node.py:50-91`：

```python
self.tts_audio_pub = self.create_publisher(
    UInt8MultiArray, "/audio/tts_pcm", audio_qos
)
self.audio_subscription = self.create_subscription(
    UInt8MultiArray, "/audio/clean_pcm", self._on_clean_audio, audio_qos
)
```

它适合音频，原因是：

- PCM 是持续产生的帧，不是一次“请求-响应”。
- 生产者和消费者需要解耦。
- 新帧比很久以前的旧帧更有价值。
- 一帧丢失不应该让整条连接报错或重试阻塞。

### 3.2 优缺点

| 优点 | 代价 |
|---|---|
| 一对多，生产者不依赖消费者 | 没有内建成功结果 |
| 异步、吞吐高 | 需要自己设计 ACK 或状态 Topic |
| DDS 可配置可靠性和历史深度 | QoS 不兼容时可能完全收不到 |
| 节点可随时加入/离开 | 事件顺序、重复和过期要由系统语义处理 |

因此候选动作先用 Topic 传递是合理的：Guard 是过滤流水线的一站。但“执行 2 秒并可取消”不应该只靠 Topic，因为 Topic 没有任务生命周期。

## 4. Service：短时请求-响应

Service 适合快速、有限、不可流式的 RPC，例如“清空地图”“查询配置”“切换模式并立刻返回是否接受”。请求方通常等待一个 response。

本项目主链没有把运动做成 Service，原因是运动可能持续数秒，还需要：

- 持续进度；
- 用户取消；
- 障碍中止；
- 服务端拒绝和超时；
- 新目标抢占旧目标。

这些都不是 Service 的强项。Lifecycle 的状态转换底层使用 service，但那是短控制操作，符合 Service 语义。

`ros2-doc/ros2-src/differential_drive_robot/srv/SetControlMode.srv` 是适合 Service 的例子：模式切换只需请求和一次结果，不需要连续 feedback。

## 5. Action：有生命周期的长任务

Action 在 ROS 2 中由 goal、feedback、result 以及 cancel 组成。项目接口位于：

- `src/embodied_agent_interfaces/action/ExecuteRobotCommand.action`
- `src/embodied_agent_cpp/src/typed_action_bridge_node.cpp`
- `src/embodied_simulation/src/simulation_control_node.cpp`

一个 `move` goal 的生命周期是：

```text
client async_send_goal
  -> server handle_goal: 接受/拒绝
  -> server handle_accepted: 启动执行
  -> publish_feedback: executing + progress
  -> succeed / abort / canceled
  -> client result_callback
```

### 5.1 为什么不让 Agent 直接成为 Action client

当前迁移设计保留了 `RobotCommand` typed Topic，再由 `typed_action_bridge` 发送 Action。优点是 Guard 与旧消费者保持兼容，Action 迁移可以独立验证；代价是增加一个进程和一次转发。长期设计可以让 Guard 直接成为 Action client，但那会把安全校验和执行协议耦合在同一节点中。

### 5.2 Topic 与 Action 的边界

| 场景 | 选择 | 原因 |
|---|---|---|
| PCM 音频帧 | Topic | 高频、连续、允许丢旧帧 |
| ASR partial | Topic | 观察事件，没有结果 |
| 动作候选 | Topic | 过滤流水线输入 |
| 执行 move/turn | Action | 持续、有进度、可取消、有终态 |
| 急停 | Topic | 必须立即广播，不等待 response |
| 生命周期转换 | Service | 短请求、确定响应 |

## 6. Parameter：启动期配置

Parameter 用于节点配置，不是高频控制通道。项目在节点启动时读取：

```cpp
capture_enabled_(declare_parameter("capture_enabled", false)),
frame_ms_(declare_parameter("frame_ms", 20)),
vad_(declare_parameter("vad_rms_threshold", 0.018))
```

配置文件和 launch override 共同决定最终值。当前代码大多只在构造或 `on_configure()` 读取参数，没有注册动态参数回调，所以运行中修改参数不一定会改变已构造对象。面试时不能笼统说“ROS 参数支持动态调参，所以这个项目可在线调 AEC”。要看代码是否在变化后重建对象或处理 callback。

## 7. Lifecycle：管理资源状态

普通 Node 构造后就开始工作。LifecycleNode 把资源准备和业务激活分开：

```text
unconfigured -> configuring -> inactive -> activating -> active
active -> deactivating -> inactive -> cleaningup -> unconfigured
```

`ActionGuardNode`：

- `on_configure()` 创建 pub/sub；
- `on_activate()` 激活 lifecycle publishers；
- inactive 时即使 subscription 收到候选，也由 `is_active()` 忽略；
- `on_cleanup()` 释放接口。

`SimulationControlNode` 还在 deactivate 时取消活动目标、调用 stop、发布零速度，再停止 timer。这是生命周期用于安全控制的真正价值，不只是“启动顺序更优雅”。

## 8. Timer：控制循环而非 sleep

`SimulationControlNode` 用 20 Hz wall timer 调用 `control_tick()`。与在回调里 `sleep(duration)` 相比：

- executor 仍能处理取消和 LaserScan；
- 每个 tick 都能重新检查安全；
- 可以发布 feedback；
- 生命周期 deactivate 可以取消 timer；
- 控制周期和任务时长解耦。

运动持续时间由 `ActionExecution` 比较时间戳判断，而不是让线程睡满 2 秒。

## 9. QoS：不是“网络优化开关”

QoS 决定 DDS 如何保存和传输样本。项目有两类选择：

### 9.1 音频和 LaserScan

`SensorDataQoS` / best effort / 小历史：

- 新数据优先；
- 不因重传旧帧增加延迟；
- 网络抖动时允许丢样本。

### 9.2 命令、结果和诊断

`QoS(10).reliable()`：

- 动作命令不能像音频帧一样随意丢；
- feedback/result/ACK 需要更稳定地到达；
- 代价是慢消费者或差网络下可能产生排队和重传。

Publisher 和 Subscriber QoS 必须兼容。调试“Topic 存在但没有数据”时，先执行 `ros2 topic info -v` 查看 offered/requested QoS。

## 10. 名称与 namespace

以 `/` 开头的是绝对名称，如 `/agent/action_candidate`；不以 `/` 开头的是相对名称，如 `robot/execute_command`。

`SimulationControlNode` 有意使用相对名称，所以放入 namespace `robot1` 后会得到：

```text
/robot1/robot/execute_command
/robot1/cmd_vel
/robot1/scan
/robot1/diagnostics
```

Agent 和 Guard 仍大量使用绝对名称，因此“整条系统天然支持多机器人 namespace”并不完全成立。当前 namespace 验证重点覆盖执行链；若要多 Agent 隔离，还需把上游绝对名称参数化或改为相对名称。

## 11. 面试回答模板

**问题：Topic、Service、Action 怎么选？**

先看数据是否是事件流、短 RPC 还是长任务。音频和雷达是高频连续数据，用 Topic 配合 best-effort QoS；生命周期切换是短请求，用 Service；运动需要接受、进度、取消和最终结果，所以用 Action。这个项目早期还有 JSON Topic 执行路径，后来增加 `RobotCommand` 和 `ExecuteRobotCommand`，就是为了让任务状态和接口类型更明确。急停仍用 Topic，因为它是必须立即广播的事件，不应等待普通任务响应。选择的核心不是消息大小，而是交互语义。
