## 1. 硬件链路与仿真链路不同

硬件默认路径：

```text
ActionGuard
  -> /robot/action_command (trusted JSON)
  -> HardwareControllerNode
  -> ActionValidator 再校验
  -> HardwareProtocol encode
  -> HardwareTransport mock/UART/SPI
  -> 下位机
```

当前硬件节点不消费 `ExecuteRobotCommand` Action，也没有读取下位机 result frame。它是协议和传输原型，任务完成闭环弱于仿真 typed Action。

## 2. HardwareTransport 抽象

接口只有：

```cpp
open(error)
send(frame, error)
name()
```

factory 根据参数创建 mock、UART、SPI。与 pluginlib 相比，这是编译期已知实现的简单 factory：新增 transport 需要修改 factory/节点分支，但部署和错误链更直接。

## 3. 帧格式

`HardwareProtocol::frame()` 构造：

```text
byte 0   0xAA          header
byte 1   0x55          header
byte 2   0x01          protocol version
byte 3   opcode
byte 4   payload length
byte 5-6 sequence      little-endian uint16
byte ... payload
last 2   CRC16-CCITT   little-endian
```

CRC 计算覆盖 header 到 payload，不覆盖 CRC 自身。初始值 `0xFFFF`，多项式 `0x1021`。

## 4. 动作 payload

### move

```text
linear_x * 1000 -> int16 little-endian
duration_s * 1000 -> uint16 milliseconds little-endian
```

例如 `linear_x=0.2, duration=1.0`：

```text
velocity = 200 = 0x00C8 -> C8 00
duration = 1000 = 0x03E8 -> E8 03
```

### turn

`angular_z * 1000` 和 duration，格式同 move。

### wave

一个 byte count。

### set_led

三个 byte RGB，例如 red 为 `FF 00 00`。

### stop

空 payload。stop 也有独立 sequence 和 CRC。

set_mode 没有在 HardwareProtocol 中实现，虽然 Guard 可接受。若发送到硬件节点，protocol 返回 unsupported hardware action。说明“接口层允许”不等于“每个后端都实现”。

## 5. 为什么 Guard 后再次校验

硬件节点订阅的是名为 trusted 的 Topic，但 ROS graph 中其他进程仍可能直接 publish。再次调用 `ActionValidator`：

- 防止绕过 Guard；
- 确保协议转换前已 clamp；
- 让 hardware node 单独运行时仍安全；
- 避免非法数值溢出到 int16/uint16。

这叫信任边界本地化：每个产生物理副作用的节点自行验证输入。

## 6. UART 实现

`open()`：

- `O_RDWR | O_NOCTTY | O_CLOEXEC | O_NONBLOCK`；
- termios raw mode；
- 设置输入/输出 baud；
- 8 data bits、1 stop bit、无硬件流控；
- flush 旧缓冲。

`send()` 处理 partial write：

```text
offset=0
while offset < frame.size:
  poll(POLLOUT, 100ms)
  write(remaining bytes)
  EAGAIN/EINTR -> retry
  offset += written
```

一次 `write()` 不保证写完整帧，所以必须循环。每一轮 poll 最多 100 ms；这是写就绪超时，不是下位机 ACK 超时。

## 7. SPI 实现

SPI 配置 mode 0、8 bits、指定 speed。send 使用 `SPI_IOC_MESSAGE(1)` 同时发送并接收等长字节。

当前接收 buffer 随后被丢弃，没有解析下位机返回、状态或 CRC。因此 SPI send 成功只表示 Linux ioctl 成功完成传输。

## 8. RAII 文件描述符

`FileDescriptor` 析构时 `close()`，`reset()` 先关闭旧 fd 再接管新 fd。这样构造后任何错误或异常退出都不会忘记释放设备。

类没有显式禁止 copy；但它只作为 transport 私有成员，而 transport 通过 `unique_ptr` 使用且没有复制路径。更严格的实现可以 delete copy constructor，防止未来误复制导致 double close。

## 9. MotionWatchdog

move/turn frame 发送成功后：

```text
deadline = now + motion_duration
```

20 ms timer 调用 `expired(now)`。到期只返回一次 true 并清空 deadline，然后 `send_stop("duration_elapsed")`。

急停也调用 `send_stop()`，先 disarm watchdog，再发送 stop。

若 stop 发送失败，代码发布 io_error，并把 watchdog 重新 arm 100 ms，形成重试。下一 tick 到期后再次尝试 stop。

## 10. ACK 的真实含义

发送命令成功后发布：

```json
{
  "status":"sent",
  "action":"move",
  "sequence":42,
  "source":"command",
  "transport":"uart:/dev/ttyUSB0"
}
```

它表示：

- JSON 已验证；
- 帧已编码；
- 主机 send/write/ioctl 返回成功。

它不表示：

- 下位机 CRC 校验通过；
- 电机驱动接受；
- 运动完成；
- 里程计达到目标。

要称为闭环 ACK，需要下位机返回带 sequence 的 accepted/completed/error frame，主机解析并映射到 Action result。

## 11. UART 与 SPI 对比

| UART | SPI |
|---|---|
| 异步串行，线少，距离相对灵活 | 同步总线，主机提供时钟，通常板级短距离 |
| baud rate | clock speed |
| 字节流，需自行分帧 | 每次 transfer 有边界但协议仍需定义 |
| 可能 partial write | ioctl transfer 通常一次提交 |
| 下位机可异步回传 | 全双工收发发生在主机发起 transfer 时 |

项目统一 frame 格式，transport 只负责送字节，避免协议逻辑复制。

## 12. 测试证据

- hardware protocol test：opcode、payload、sequence、CRC、watchdog。
- hardware transport test：伪终端验证 UART 实际写出完整 frame，非法 baud 被拒绝。
- mock smoke：无需真实设备验证节点和 ACK。

没有真实 SPI/UART 下位机完成确认测试，因此硬件执行性能和可靠性仍需目标设备验收。

## 13. 面试回答模板

**问题：硬件通信如何保证安全？**

硬件节点即使消费 Guard 后的 Topic，也会本地再次做 schema、白名单和限幅，防止其他 ROS 节点绕过 Guard。协议帧包含固定帧头、版本、opcode、payload 长度、sequence 和 CRC16；速度和时长缩放为整数后用 little-endian 编码。UART 使用 nonblocking fd、poll 超时和 partial-write 循环，SPI 用 spidev ioctl，文件描述符由 RAII 管理。move/turn 发送后 watchdog 按 duration 到期主动发 stop，stop 失败每 100 ms 重试。但当前 ACK 只表示主机侧 send 成功，没有解析下位机完成帧，所以不能把它包装成真实运动闭环。
