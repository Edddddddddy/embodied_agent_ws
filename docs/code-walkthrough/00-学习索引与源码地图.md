## 1. 先建立正确心智模型

这个项目不是“一个 Python 程序调用一个机器人 API”，而是多个 ROS 2 节点组成的流水线。节点之间只通过 ROS 接口交互，所以任何一段都可以被 mock、在线实现、离线实现、Gazebo 或硬件实现替换。

一条成功的语音运动命令可以压缩为：

```text
麦克风 PCM
  -> audio_frontend: AEC / VAD / 静音断句
  -> online_agent 或 offline_agent: ASR / 唤醒 / LLM / 动作解析
  -> action_guard: C++ schema 校验、白名单、限幅
  -> typed_action_bridge: RobotCommand Topic 转 ExecuteRobotCommand Action
  -> simulation_control: BT + ActionExecution + RobotExecutor
  -> GazeboRobotExecutor: 雷达安全、速度斜坡、/cmd_vel
  -> ros_gz_bridge -> TurtleBot3
```

反向证据链是：

```text
/odom 位移 <- Gazebo 物理世界
/robot/action_result <- Action 终态
/robot/bt_status <- BT 阶段与结果
/robot/action_ack <- executor 已接收/处理
/diagnostics <- 生命周期、后端、传感器与安全状态
```

只看到 `/agent/action_candidate` 不能证明机器人执行，只看到 `/robot/action_ack` 也不能证明发生了物理位移。

## 3. 运行时节点

典型 Gazebo typed-action 模式包含：

| 节点 | 进程/部署 | 输入 | 输出 |
|---|---|---|---|
| `audio_frontend` | 独立 C++ 进程 | 声卡、`/audio/tts_pcm` | `/audio/clean_pcm`、`/audio/silence_timeout` |
| `online_agent` 或 `offline_agent` | 独立 Python 进程 | clean PCM、text input | ASR、回复、action candidate、TTS PCM |
| `action_guard` | Lifecycle C++ 进程 | `/agent/action_candidate` | legacy/typed trusted command、reject |
| `typed_action_bridge` | C++ 进程 | typed command Topic | Action goal、feedback/result 观察 Topic |
| `simulation_control` | Lifecycle 进程或 component | Action、LaserScan、急停 | `/cmd_vel`、ACK、状态、诊断 |
| `ros_gz_bridge` | 外部组件 | ROS/Gazebo 消息 | `/scan`、`/odom`、`/cmd_vel` 跨域转换 |
| `nav2_lifecycle_manager` | 外部组件 | lifecycle services | configure/activate 节点 |

注意：在线和离线 Agent 是替代关系，正常部署不会让它们同时消费同一个麦克风流。

## 4. 线程地图

“节点”和“线程”不是一回事。一个节点内部可以有多个工作线程：

| 位置 | 线程 | 这样做的原因 |
|---|---|---|
| AudioFrontend | PortAudio input callback | 只搬运 PCM，必须短小、不可阻塞 |
| AudioFrontend | processing thread | 执行 AEC/VAD 和 ROS publish |
| AudioFrontend | playback thread | 写声卡，并把播放流送入 AEC reference |
| OnlineAgent | ROS executor 主线程 | 接收 Topic 回调 |
| OnlineAgent | 每轮 `_run_turn` 线程 | 网络 LLM 不能阻塞 ROS 回调 |
| OnlineAgent | TTS worker | 与 LLM token 消费重叠 |
| OfflineAgent | ASR worker | 保证 sherpa stream 只被一个线程访问 |
| OfflineAgent | turn/TTS/audio workers | 形成 LLM、合成、发布三级流水线 |
| SimulationControl | 2-thread executor | 控制回调与诊断回调可并行 |

线程隔离的共同原则是：实时或高频回调只做有界工作；网络、模型、磁盘和可能阻塞的 I/O 移到工作线程。

## 5. 三条必须会追的调用链

### 5.1 文本命令到机器人运动

1. `OnlineAgentNode._on_text_input()` 接收 `/agent/text_input`。
2. `_accept_transcript()` 经过 `WakeWordGate`，用锁设置 `_busy`。
3. `_run_turn()` 流式消费 LLM；`TaggedStreamParser` 分离 speech/action。
4. `_publish_actions()` 发布 `/agent/action_candidate` JSON。
5. `ActionGuardNode::on_candidate()` 调用 `RobotCommandAdapter::convert()`。
6. `ActionValidator::validate()` 做 schema、白名单和 clamp。
7. Guard 同时发布 legacy JSON 与 `RobotCommand`；typed 模式只消费后者。
8. `TypedActionBridgeNode::on_command()` 发送 `ExecuteRobotCommand` goal。
9. `SimulationControlNode::handle_accepted()` 启动 BT、executor 和 `ActionExecution`。
10. 20 Hz `control_tick()` 调用 executor `step()`，发布 `/cmd_vel`。

### 5.2 扬声器回声到干净音频

1. Agent 发布 `/audio/tts_pcm`。
2. AudioFrontend 将 PCM 放入播放队列。
3. playback thread 先 `add_reference()`，再 `Pa_WriteStream()`。
4. 麦克风 callback 把采集帧放入 input queue。
5. processing thread 调用 `NlmsEchoCanceller::process()`。
6. clean PCM 发布给 ASR，同时经 `EnergyVad` 和 `SilenceDetector` 判断断句。

### 5.3 障碍物打断运动

1. `/scan` 回调更新前/左/右最近距离和时间戳。
2. `SimulationController::step()` 发现前方距离小于 emergency threshold。
3. 输出 `safety_stopped=true` 且前进线速度归零。
4. `ActionExecution::update(..., blocked=true)` 返回 `kBlocked`。
5. ReactiveSequence 重新 tick `CheckSafety`，BT 返回 blocked。
6. `finish_active_action()` 调用 executor `stop()` 并 abort Action result。

## 6. 两种“导航”不要混讲

主项目中的运动是“给定速度，运行给定时长”：

```text
move(linear_x=0.2, duration_s=1.0) -> 约走 1 秒
```

它不知道目标点 `(x, y, yaw)`，也没有全局地图、路径规划或定位闭环。`nav2_cpp_tutorial` 的导航则是：

```text
NavigateToPose(map frame goal)
  -> 全局规划器生成 path
  -> 局部控制器结合 costmap 输出速度
  -> BT 处理恢复、重规划、取消和结果
```

面试时可以说主项目已完成可靠动作执行链，Nav2 示例证明自己理解目标点导航；不能说语音主项目已经完成复杂自主导航。
