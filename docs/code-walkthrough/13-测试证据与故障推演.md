## 1. 测试的核心问题

测试不只是“代码能跑”，而要回答每层承诺由什么证据证明。一个端到端 PASS 不能替代边界单测，一个单元测试也不能证明 Gazebo 真的移动。

## 4. typed Action 集成测试如何证明闭环

`test_typed_action_server.py` 不启动 Gazebo，而是：

- 自己发布合成 LaserScan；
- 直接作为 Action client；
- 订阅 `/cmd_vel` 和 BT status；
- 对每个 goal 等 result。

覆盖：

```text
UNKNOWN -> BT validate/rejected
MOVE -> feedback/executing -> success -> final zero velocity
MOVE + cancel -> canceled -> zero velocity
MOVE + 0.1m scan -> safety/blocked -> zero velocity
TURN + short hard timeout -> timed_out
active TURN + STOP -> old goal preempted
```

它证明 Action/BT/controller 接口，不证明 Gazebo bridge 或 odom。

## 5. Gazebo 测试为何更强

`test_gazebo_motion.py` 同时要求：

- scan 到达；
- odom 到达；
- action pipeline 有 subscriber；
- executor ACK；
- typed 模式下 result success 和 BT confirm；
- 起止 odom 距离大于 0.08 m；
- 位移不超过 0.5 m，排除异常跳变。

这形成“命令、控制、物理观测”联合证据。仍然是仿真，不等于实体硬件。

## 6. 分层故障定位方法

不要看到“机器人不动”就重启所有节点。沿数据流找最后一个正常证据：

```text
1 clean PCM?
2 ASR final?
3 action candidate?
4 Guard trusted command or rejection?
5 Action goal/feedback?
6 BT status?
7 cmd_vel?
8 bridge/Gazebo?
9 odom movement?
```

最后一个正常点和第一个异常点之间就是故障范围。

## 8. 故障推演

### 8.1 clean PCM 有频率但 ASR 无 partial

检查：

- publisher/subscriber QoS 是否兼容；
- online key、WebSocket、SDK callback；
- offline worker 是否存活、queue 是否积压；
- PCM 是否真为 16 kHz mono int16。

### 8.2 有 partial 但没有 final

检查 `/audio/silence_timeout`。若没有，记录 RMS 看 VAD threshold；若有，检查 commit 是否入队/发送以及 ASR provider 是否返回 completed。

### 8.3 final 正确但没有 action candidate

检查 wake gate：final 是否含唤醒词或处于 active window；查看 recognition feedback。再检查 Agent busy、LLM 输出标签和 fallback 阻断。

### 8.4 candidate 有但 Guard 无输出

检查 Lifecycle active。再监听 `/robot/action_rejected`，确认 exact keys、类型和白名单。Guard inactive 是静默忽略，不会 rejection。

### 8.5 typed command 有但 Action result server unavailable

检查 SimulationControl lifecycle、Action 名称、namespace、typed bridge 是否与服务端处于同一命名空间。

### 8.6 Action accepted 立即 blocked

看 `/robot/simulation_state` 和 diagnostics：`scan_timeout` 表示没有新 scan，`front_emergency` 表示前方距离过近。检查 SensorData QoS 和 bridge。

### 8.7 `/cmd_vel` 非零但 Gazebo 不动

检查 ros_gz_bridge、Gazebo command topic、模型控制插件、仿真是否 pause、TurtleBot3 model 名称。此时上游 Agent/Guard 通常已经正常。

### 8.8 Action success 但 odom 不变

ActionExecution 按时间成功，不独立验证里程。因此可能是 bridge/模型/轮子问题。必须把 odom 或其他反馈纳入成功条件，才能形成位置闭环。

### 8.9 plugin configure 失败

看 lifecycle transition 日志。检查：

- plugin name 是否与 XML 一致；
- library/description 是否安装；
- BT XML 是否可读；
- obstacle distance 是否大于 emergency distance；
- control rate 和 timeout 是否正数。

### 8.10 UART ACK 没有完成状态

当前设计本来就只有 host `sent`。若 send 失败看 hardware status；若要完成确认，需要下位机返回帧，不能靠延长等待推断成功。

### 8.11 emergency stop 后速度为零但 Action 仍 active

这是当前实现可以出现的行为，不一定是 DDS 丢消息。`on_emergency_stop()` 调用 executor stop，却没有结束 `active_goal_`；控制器内部的 latched emergency flag 也没有通过 executor 接口被设置。查看 `/cmd_vel` 会看到零速，但 Action 可能继续反馈直到 duration 完成。生产修复应把“停车、Action canceled/blocked、拒绝新运动、显式 reset”设计成一个原子安全状态转换。

## 9. 故障注入练习

按顺序做，每次先预测结果：

1. 把 Guard 保持 inactive，发布 candidate。
2. 发布多一个 JSON argument。
3. 不发布 scan，发送 forward goal。
4. 运动中把 scan 距离改为 0.1 m。
5. 运动中发送 cancel。
6. active move 后立即发送 stop goal。
7. 把 executor plugin 写成不存在名称。
8. 使用不支持 baud 启动 hardware controller。
9. 运动中发布 `/robot/emergency_stop`，分别记录速度和 Action 状态。

记录每次最后一个正常 Topic、result status、BT stage 和 final `/cmd_vel`。

## 11. 面试回答模板

**问题：如何证明系统真的执行了命令？**

我采用分层证据而不是只看 Topic publish。单元测试先证明 parser、Guard、ActionExecution、BT 和 controller 的边界；ROS mock 测试直接发 typed goal，覆盖 accepted、feedback、success、cancel、blocked、timeout、preempt，并要求终态 `/cmd_vel` 为零；Gazebo 测试再联合检查 scan、Action result、BT confirm、executor ACK、非零速度和 `/odom` 位移。排障时沿 clean PCM、ASR final、candidate、trusted command、Action、BT、cmd_vel、odom 找最后一个正常点。这样能区分模型失败、ROS 接口失败、控制失败和物理后端失败。实体硬件仍需独立回传和外部观测，仿真结果不能替代。
